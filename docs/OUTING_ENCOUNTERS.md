## 无打卡、无额外资源

- 条件来自服务端生成并保存的会话 ID，不读取现实时间、定位、天气或客户端偏好。不要求傍晚、夜里上线。
- 原 ID 前 6 位十六进制数 `% 48 / 12` 决定虚构晨昏；接下来一个字节 `% 4 == 0` 才有偶遇。钓鱼要求月夜（3）、散步要求晚霞（2）。在均匀 ID 的组合空间中各占约 1/16；不是对真人游玩样本的频率测量。
- 同一会话不会因为重复提竿、发现点、刷新或暂停重新抽取。相同类型只记第一次的日期和来源 ID，后来不同会话再次遇见也不覆盖。
- 不改鱼种、路线、等待时长、咬钩/障碍概率、金币、成长、照顾习惯或偏好结算；不调用额外 RNG，不增加计时器。
- 首次记录会在现有日记留下一条“你们遇见了一处特别风景，已收进风景手记。”放弃本局保留已经发生的发现和手记，但不获得结算奖励。

## 存档与安全边界

- schema 13 → **14**，不倒填过去的偶遇。普通旧记录不新增来源 ID；升级前已在进行的合格会话，可以在升级后真正发生的下一次发现留下新手记。
- 新偶遇条目使用可选 `outingId` 保存来源；只允许这两种偶遇携带它。验证合法小写会话 ID、对应游戏/虚构晨昏/选择条件、`shared` 来源、纪念册时间约束，以及已有鱼类/沿途发现的时间区间证据。不把本地 JSON 当作密码学防伪凭证。
- 纪念册上限由 29 增至 31。前端保护可选字段的类型；完整资格和日期验证由服务端负责。
- 正常事务同时保存发现与回忆；重试不能重复记录。旧档升级先快照，仅迁移版本和正常修订号，不改历史。JSON 备份往返保留原日期/来源，坏导入不能破坏当前存档。导入仍按原规则清除进行中的游戏，不恢复会话控制权。
