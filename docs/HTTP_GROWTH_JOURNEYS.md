# 从新蛋到成年：完整 HTTP 成长旅程

## 范围（2026-10-20）

补齐既有两类证据之间的空白：存储层已经有十角色 × 四策略的 [40 条旅程](GROWTH_JOURNEYS.md)，浏览器已有 [三键跨阶段回归](CARE_GROWTH_JOURNEY.md)，但后者明确构造了接近成长阈值的输入。最初接入四条星星狸的**从新蛋开始、不赋值成长历史的真实 HTTP 旅程**；现已扩到十角色×四策略，共40条命名旅程。

没有发现必须修改成长规则的新缺陷；不改变成长速度、三键、奖励、存档格式或旧档迁移。最初的生产改动仅把 Handler 内七处服务时间读取接到私有时钟参数，公开 `Handler` 始终传 `time.Now`；本轮扩充只改测试及文档。没有新增配置、客户端时间字段、调试接口或测试加速入口。

## 测试方式

`internal/httpapi/growth_journey_test.go` 使用真实 `httptest.NewServer`、HTTP 客户端、JSON、现有路由/请求头和独立临时 SQLite。孵化、照顾、五次接星星动作、睡眠、回访、导出、导入、重启均走同一 Handler。

- 只控制服务端时钟；不直接调用 Store 操作养宠，不使用 SQL 写状态，不导入构造的需求、成长点、习惯、形态或里程碑时间。导入的 JSON 原样来自这一只宠物之前的 HTTP 导出。
- 起始时钟比测试进程当前时间晚一小时，避开 Store.Open 初始化新蛋时使用的现实时间；不改变产品的初始化逻辑。
- 当前使用十只角色×四策略；每条都经HTTP选择实际角色，明确核对种类与默认名字，并在后续响应、跨安装恢复和重开中保持。最初仅星星狸四策略是历史验收范围，不再作为当前上限。
- 四十条旅程共用一个受控起始时刻。相同照顾策略下，十角色的成长/成年相对时刻、四种形态及定型依据必须完全相同；每只角色的三种照顾策略也分别与其无照顾旅程比较。角色不是隐藏难度选项。
- 从孵化开始模拟至第 216 小时，再检查成年后 48 小时睡眠等边界。不是实际等待 216 小时，也不是浏览器三键或自然多日认证。

## 旅程与断言

1. GET 获取代次，再经 reset / hatch 正常得到零成长点幼年宠物。
2. 完整离开 48 小时后 visit：需求必须为饱食 44、心情 50、清洁 66、体力 61；仅结算 12 小时、成长 12.255 点，主动照顾次数为零。回访小结仍记录真实 48 小时间隔。
3. 幼年原样导出并导入另一新安装，关闭重开后继续养；首次进入成长期再次跨安装恢复后继续。导出含下载/no-store 头；携带源安装代次导入目标须 409 `save_changed` 且不改目标，新代次导入成功且轮换代次。
4. 策略分别为每 12 小时回访但不照顾、按需喂食/清洁/睡眠、增加完整陪玩、按历史平衡陪玩。所有需求与历史从实际动作累积。每个响应校验存档有效、身份保持、成长/习惯不倒退、成长日期不改写。
5. 喂食及睡眠的相同 requestId 重试不重复照顾或反向切换睡眠；错误睡眠意图头必须 409 `sleep_changed`，再读状态不变。正确意图和重试都经过实际 HTTP 请求。
6. 每次出现待呈现小结都尝试确认：睡眠中不能领取，清醒且不在游戏时只能确认一次，确认不改变宠物状态。
7. 第 120 小时重开数据库/HTTP 服务，保持状态与代次；成年后再导出、跨安装恢复，成长日期、形态、定型依据保持。
8. 孵化、成长、成年、相识 1 天及 7 天纪念各一条。定型依据的累计时长对应实际越过阈值的时刻，而非稍后的 HTTP 请求时间；初次长离开丢弃的 36 小时不计入成长。
9. 成年后仍可有效恢复体力、积累休息习惯；48 小时睡眠只结算 12 小时，满体力继续睡不虚增有效休息。之后再次重启、导入，定型证据仍不变。

当前十角色在相同策略下得到相同的模拟结果（小时从孵化算起，非建议上线频率）：

| 策略 | 进入成长期 | 成年 | 形态 | HTTP 请求数 |
|---|---|---|---|---:|
| 无照顾 | 63:03:02.948 | 156:49:58.125 | 自在型 | 91 |
| 安稳照顾 | 58:36:53.010 | 104:34:47.737 | 恬静型 | 667 |
| 增加陪玩 | 57:00:00.000 | 93:07:58.640 | 活力型 | 1100 |
| 平衡照顾 | 57:01:01.704 | 97:48:01.179 | 均衡型 | 766 |

同一规则下三种照顾策略均比无照顾更早成年。数字只描述这些固定测试策略，不承诺真人游玩必然有相同成长日期。
