# 开局准备与玩法规则中的当前奖励额度（2026-10-20）

## 为什么补充

游戏选择页已经显示共享额度和钱包约束，但进入首次教学、再次开局准备卡或暂停规则后，只剩静态的基础奖励范围。额度为零时仍能陪玩本来就是正常设计；本批是把现有约束讲清楚，不是修复“可以超额产币”，也不改变陪玩或奖励条件。

## 行为

- 七款共用 `GuideReward`：保留每款的完成条件/基础范围，并明确标为“基础规则”。在再次开局准备卡、首次/重看/暂停教学的奖励页，补充当前额度说明；操作教学首页不重复奖励区。
- 依据已接受的 `economy`、`shop` 和服务端同步时间，复用已有 `gameAllowance`。明确区分额度为零、钱包已满、钱包空间不足、普通剩余额度、旧服务缺少钱包上限及规则/经济信息未同步。
- 不承诺保底金币：共享额度不是单局奖励，也不是预留额度，实际按完成情况和结算时约束决定。零额度文案不假定原因是“今日已领完”，兼容存档时间领先的回退保护。
- 不创建新存档字段、不改奖励算法，不新增按键或 LCD 点击控件；不把“当前不能得币”变成禁玩。说明随正常响应和 UTC 日期边界更新，不主动写请求、自动续局或播报倒计时。
- 自动结算的接星星/连连看也使用“结算时”而非暗示必须手动收好。

## 验证方式与边界

- `web/src/GuideAllowance.test.tsx`：七款 × 首次奖励页/重复开局/暂停规则，额度与钱包边界、缺失旧字段、UTC 边界、正常 App 读取更新，保留规则及三键和无玩法写入断言。
- `scripts/check-guide-allowance.mjs`：独立构建、随机端口、临时 SQLite，通过 HTTP 导入**构造的**钱包和额度；首次钓鱼/再次散步 × 五种额度钱包状态 × 三种视口，检查文本、原生滚动可读、无裁切、仅三键、阅读不写数据，以及零额度/满钱包仍可按 B 开局。拒绝玩家构建路径及其符号链接。
- 浏览器只验证说明与开局，不冒称30局自然游玩结算，也不把构造的币数说成游戏赚取。奖励结算仍由既有后端测试覆盖。
- 玩家 18102 服务、`data/pixelpet.db`、`bin/pixelpet`、`web/dist` 不部署、不覆盖。本批不代表实体手机或自然多日验收。
