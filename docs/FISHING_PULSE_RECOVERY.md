# 池塘自动计时失败后的安全恢复 · 2026-10-19

## 问题与修复

钓鱼的自动 `fish-step` 原先没有处理 `act()` 返回失败。请求真正跨过一次渲染后被拒绝时，忙碌状态解除会重新挂上旧步数的定时器，约 80ms 后再次发送同一步。一个立即拒绝的模拟 Promise 可能把忙碌状态更新合并掉，掩盖此问题；新增回归保留待决请求跨渲染，旧实现确实出现两次脉冲而不是一次。

现在自动脉冲未成功确认后，会使本地钓鱼会话失效，停止自动计时并读取当前存档，不重发旧写入。同步成功后保持本地暂停，玩家再按 C 明确继续；读取也失败时，沿用连接恢复界面，B 只同步，A/C 不执行玩法。已知拒绝沿用 `visit` 同步，结果未知沿用 `state` 核对，不拿回访认领代替核对。

- 请求已保存但回复丢失：保留服务端已确认的那一次进度，不回滚、不再补一次。
- 另一窗口改变了步数：读到当前步数，再由 C 发起新会话，不反复提交旧步数。
- 另一窗口已完成三竿：展示真实结果，不自动收好或丢弃。
- 等待与咬钩两个阶段都覆盖，不额外消耗竿数、发现、照顾或金币。

生产改动仅钓鱼计时器的失败分支，与其他实时小游戏已有恢复方式一致。A/B/C 三键、鱼种、等待/咬钩时长、成长与照顾条件、成年定型、奖励及 schema 11 全部不变。局部暂停是浏览器会话保护，不是为存档新增暂停字段；服务端仍使用原有租约规则。

## 真实 Chrome 验证

独立临时库完成 **15 场景**，不是用户试玩反馈：

- **14 个故障场景**：320 / 390 / 1200px × 普通 / 双倍根字号 × 服务端真实拒绝 / 写入成功但回复丢失，共 12 组；再补咬钩时拒绝、等待时丢回复两组。双倍字号组同时使用强制配色与减少动态效果，手机尺寸触摸实体键、桌面使用键盘。
- 拒绝由另一次真实 API `fish-resume` 改变步数产生，原请求得到服务端 400；丢回复先让真实服务保存原请求，再中断响应，不伪造成功存档。
- 部分场景继续中断同步读取，检查 A/C 禁用，B 恢复连接而没有重发脉冲；恢复后读到真实进度，由新的 C 明确开始。失败后等待 1700ms 无重复写入，后续也只有新会话的有效计时。开竿数、发现、照顾与金币不因失败增加。
- 14 场景全部检查无横向溢出、文字位于 LCD 内、正文随根字号放大、三个至少 44px 实体键、无 LCD 内玩法控件与浏览器异常。普通/大字截图 `fishing-recovery.png`、`fishing-recovery-large-text.png` 已人工检查。
- **1 场自然完整对局**：重新准备临时宠物，真实 B 开竿、按实际等待时长等到咬钩，再 B 提竿，连续三竿并 B 收好；不跳过等待或强制咬钩。实际产生 3 次 cast、3 次 reel、1 次 finish，图鉴总发现 3 条、照顾 1 次、金币 6，未提前结算。

边界：故障场景的咬钩起点使用独立临时 SQLite 确定性夹具；它不是自然等待的证据。完整三竿对局才是未加速的等待验证。旧响应和其他窗口终局组合由应用回归覆盖，不宣称浏览器跑了所有组合或真实手机系统后台。
