# 节奏拍手：开工前离线时序评估（2026-10-19）

**状态：候选方案，未实现游戏、无可玩原型、无奖励或存档改动。** 本文只验证一组明示假设的算术，不是设备/网络测量，更不是用户试玩反馈。现有六款游戏的速度不变，森林寻宝仍后置。

## 要避免的一个协议错误

候选操作仍是 A 左 / B 右 / C 暂停，视觉文字与形状提示，不依赖声音。现在先比较这样一种简单交互：服务端发出一个提示，客户端收到并画出后才开始相同长度的预告，然后玩家回应。**没有预先同步目标时间、没有延迟补偿**。

假设服务端发出提示的时刻为 0，预告长度为 P：

- 服务端的目标时刻是 P。
- 客户端显示「现在按」的时刻是 下行耗时 + 绘制延迟 + P。
- 按键到达服务端的时刻还要加 假设的回应延迟 + 上行耗时。
- 因此相对服务端目标晚到：**RTT + 绘制延迟 + 回应延迟**。额外的两段抖动各再加一次。

这里 RTT 是往返耗时，不是单程；不能把 800ms RTT 重复算成 1600ms。P 在这个模型里抵消，单纯加长两边相同的预告，不能消除判定偏差。

现有 `web/src/App.tsx` 用 `serverTime - Date.now()` 在收到响应时更新显示时钟偏移。它适用于现有显示与粗粒度步进，但没有扣除下行耗时，**不能直接当成新游戏精确节拍校准或客户端成绩凭证**。本批没有改现有时钟，也没有证明它导致现有玩法错误。

## 结论与不能声称的事

1. **这个简单协议不能配窄判定窗口。** 表中窄窗口会拒绝很多按了正确键的假设输入；这不意味着所有联网节奏游戏都不可行，只否定这一组交互/时序假设。
2. **宽窗口值得继续讨论，但尚未证明公平。** 1800ms 在本表无额外抖动样本中全接纳，800ms RTT 的压力组仍拒绝 14 组；不能只保留通过案例宣称「延迟已解决」。长绘制卡顿也会越界。
3. **需要先解决视觉截止与服务器截止的一致性。** 不能把服务端窗口原样从客户端收包时重新倒数，否则屏幕仍说能按、服务器却已拒绝。原型应明确单调本地计时、服务端拍序/目标/截止与可解释的时钟不确定性；不以客户端时间戳、客户端命中数或自报延迟决定奖励。
4. **连接不稳应中性暂停，不把网络卡顿判成玩家失误。** 如何识别及何时暂停仍须真实协议/浏览器验证，不是这个算术脚本已经实现。后台/刷新/卡住后不补拍、回来手动继续，旧拍/重复输入不能多结算。
5. **时长只能先给名义值。** 12 拍 × 3 秒 = 36 秒可作为无暂停的原型节奏起点；预告、收好、网络等待和重新同步都可能增加时间，不能保证每局一定 30–45 秒。这里的拍数、窗口、拍距都未写入游戏规则。

## 进入原型前后的门槛

- 先收现有六款真实试玩反馈；本轮尚无新反馈，不代替用户判断「舒服」。离线评估不等于越过原型门槛。
- 再做**无奖励原型**，用 A/B/C 完成预告、回应、暂停、取消/确认放弃；静音和减少动态效果同样可辨别左右与时机。
- 实际测试键盘/手机触摸、低帧率、真实注入 100/300/800ms RTT、上下行不对称/抖动/丢请求、前后台和刷新。记录可见提示与服务端判定的差异，不能以本表替代。
- 协议公平性与用户体验过关后，再接会话/幂等/导入迁移/共享金币/成长间隔/真实纪念与兴趣，旧成年形态保持不变。十只×三阶段沿真实爪/翼/鳍/身体参与，不套通用人手。
