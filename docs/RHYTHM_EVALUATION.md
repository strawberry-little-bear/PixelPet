# 节奏拍手：开工前离线时序评估（2026-10-19）

**本文为历史算术评估，不是游戏验收。** 2026-10-20 已另做[独立无奖励原型](../prototypes/rhythm/README.md)，尚未接入正式菜单或存档；当前正式游戏七款（含[森林寻宝](TREASURE_RULES.md)）。下面的简单协议、假设与结果仍原样保留，不能当作新版原型的实测值或真人反馈。

## 要避免的一个协议错误

候选操作仍是 A 左 / B 右 / C 暂停，视觉文字与形状提示，不依赖声音。现在先比较这样一种简单交互：服务端发出一个提示，客户端收到并画出后才开始相同长度的预告，然后玩家回应。**没有预先同步目标时间、没有延迟补偿**。

假设服务端发出提示的时刻为 0，预告长度为 P：

- 服务端的目标时刻是 P。
- 客户端显示「现在按」的时刻是 下行耗时 + 绘制延迟 + P。
- 按键到达服务端的时刻还要加 假设的回应延迟 + 上行耗时。
- 因此相对服务端目标晚到：**RTT + 绘制延迟 + 回应延迟**。额外的两段抖动各再加一次。

这里 RTT 是往返耗时，不是单程；不能把 800ms RTT 重复算成 1600ms。P 在这个模型里抵消，单纯加长两边相同的预告，不能消除判定偏差。

本文评估时，`web/src/App.tsx` 使用 `serverTime - Date.now()` 更新显示时钟偏移。2026-10-20 的[显示校时修复](APP_CLOCK_SYNC.md)已改为接受响应时锚定 `serverTime`，并以 `performance.now()` 的单调经过时间推进显示及自动步进等待，避免本机日期跳变影响运行。这仍未测量或扣除下行耗时，**不能直接当成新游戏精确节拍校准或客户端成绩凭证**；本篇假设算术不等于现有玩法故障证明，也不等于节奏原型验收。

## 可复现的假设，不是实测分布

在项目根目录运行（只需 Node.js，无第三方包）：

```sh
node --test scripts/evaluate-rhythm.test.mjs
node scripts/evaluate-rhythm.mjs
```

脚本只输出 JSON，不请求服务器、不读写文件、不接触任何数据库。测试覆盖公式、RTT 单次计入、上下行独立抖动、窗口边界、非法输入、确定性和故意保留的失败案例。

枚举：基础 RTT 0/100/300/800ms；额外上下行抖动分别取 0/100/300ms；绘制延迟 16/67/200ms；回应延迟 80/200/400/600ms。**这些都是人为选的样本，不代表玩家反应速度、触摸开销或实际帧率的测量。** 无额外抖动每档 12 组，其余抖动组合每档 96 组，共 432 组；不是随机样本，不能换算成玩家成功率。

## 结论与不能声称的事

1. **这个简单协议不能配窄判定窗口。** 表中窄窗口会拒绝很多按了正确键的假设输入；这不意味着所有联网节奏游戏都不可行，只否定这一组交互/时序假设。
2. **宽窗口值得继续讨论，但尚未证明公平。** 1800ms 在本表无额外抖动样本中全接纳，800ms RTT 的压力组仍拒绝 14 组；不能只保留通过案例宣称「延迟已解决」。长绘制卡顿也会越界。
3. **需要先解决视觉截止与服务器截止的一致性。** 不能把服务端窗口原样从客户端收包时重新倒数，否则屏幕仍说能按、服务器却已拒绝。原型应明确单调本地计时、服务端拍序/目标/截止与可解释的时钟不确定性；不以客户端时间戳、客户端命中数或自报延迟决定奖励。
4. **连接不稳应中性暂停，不把网络卡顿判成玩家失误。** 如何识别及何时暂停仍须真实协议/浏览器验证，不是这个算术脚本已经实现。后台/刷新/卡住后不补拍、回来手动继续，旧拍/重复输入不能多结算。
5. **时长只能先给名义值。** 12 拍 × 3 秒 = 36 秒可作为无暂停的原型节奏起点；预告、收好、网络等待和重新同步都可能增加时间，不能保证每局一定 30–45 秒。这里的拍数、窗口、拍距都未写入游戏规则。

## 进入原型前后的门槛

- 先收现有游戏的真实试玩反馈；本轮尚无新反馈，不代替用户判断「舒服」。离线评估不等于越过原型门槛。
- 再做**无奖励原型**，用 A/B/C 完成预告、回应、暂停、取消/确认放弃；静音和减少动态效果同样可辨别左右与时机。
- 实际测试键盘/手机触摸、低帧率、真实注入 100/300/800ms RTT、上下行不对称/抖动/丢请求、前后台和刷新。记录可见提示与服务端判定的差异，不能以本表替代。
- 协议公平性与用户体验过关后，再接会话/幂等/导入迁移/共享金币/成长间隔/真实纪念与兴趣，旧成年形态保持不变。十只×三阶段沿真实爪/翼/鳍/身体参与，不套通用人手。

详见 [PLAYTEST.md](PLAYTEST.md)。当前七款正式游戏；节奏只进入独立、无奖励的交互与时序观测阶段。原型的合成延迟、自动化暂停和布局验证不代表上述门槛全部通过，生产化及真人体验仍待验证。

## 当前原型的独立观测入口

上述表格保留为历史协议假设，不能用于宣称当前原型的公平性。当前原型另有 `scripts/measure-rhythm-timing.mjs`：实际运行隔离的 Chrome 客户端与实验 HTTP 协议，记录提示 DOM、原生输入、往返与服务端收包偏差，并核对高 RTT／卡帧中性暂停。环境、复跑方法和不能据此声称的结论见[原型的浏览器时序观测](../prototypes/rhythm/README.md#浏览器时序观测)。这仍是合成网络和受控帧调度的少量自动化观测，不替代真实设备、网络或正式接入门槛。
